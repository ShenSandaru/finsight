# Structured Financial Research Reports Architecture (Sprint 10.4)

## 1. Overview & Objectives

In **Sprint 10.4**, FinSight was extended with asynchronous **Structured Financial Research Report generation** backed by an ARQ/Redis worker pool and exposed via standard REST API endpoints.

### Core Principles:
1. **Reuse of Verified Multi-Agent DAG**:
   - The report worker does **NOT** recreate or fork the research pipeline.
   - It directly invokes `FinancialResearchService.execute_research()` and uses the returned, audited, and grounded `ResearchState`.
2. **Deterministic Report Compilation**:
   - Compiles full publication-ready GitHub Flavored Markdown reports from already verified financial findings, ratios, YoY growth rates, CAGR, trends, and cross-document comparisons.
   - Zero additional LLM calls are made for markdown compilation.
3. **Single LLM Call Guarantee**:
   - Executive summaries are generated by `SynthesisNode` (1 Gemini call).
   - Entire report pipeline utilizes exactly **1 LLM call**.
4. **Safety & Guardrails Validation**:
   - Before a report status is marked `completed`, its contents and citations pass deterministic validation via `ResponseGuard`.
5. **Multi-Document Isolation**:
   - Reports support optional `document_ids: list[UUID]` filtering, strictly scoping vector retrieval to selected filings.

## 2. Report Lifecycle & Architecture

```mermaid
graph TD
    Client[Client / Analyst] -->|POST /api/v1/reports| API[FastAPI Reports Router]
    API -->|1. Create Report(status='pending')| DB[(PostgreSQL reports)]
    API -->|2. Enqueue generate_financial_report| Redis[(Redis Queue)]
    API -->|3. Return HTTP 202 Accepted| Client
    Redis -->|4. Pick up job| Worker[ARQ Worker]
    Worker -->|5. Update status='processing'| DB
    Worker -->|6. execute_research(query, document_ids)| LangGraph[FinancialResearchService Multi-Agent DAG]
    LangGraph -->|7. Return Audited Findings & Synthesis| Worker
    Worker -->|8. Compile Markdown Report| Compiler[ReportService.compile_markdown_report]
    Compiler -->|9. Validate Output| Guard[ResponseGuard]
    Guard -->|10. Persist status='completed', findings, citations, content| DB
    Client -->|GET /api/v1/reports/{id}| API
    API -->|Return ReportResponse| Client
```

## 3. Database Schema (`reports` Table)

Migration `0005_enhance_reports_schema.py` extended the `reports` table:

| Column | Type | Description |
|---|---|---|
| `id` | `UUID` (PK) | Unique report identifier |
| `title` | `VARCHAR(255)` | Report title |
| `query` | `TEXT` | User's research topic or prompt |
| `report_type` | `VARCHAR(50)` | Format type (default: `'financial_research'`) |
| `status` | `VARCHAR(50)` | State: `'pending'`, `'processing'`, `'completed'`, `'failed'` |
| `document_ids` | `JSONB` | List of scoped document UUIDs (nullable) |
| `executive_summary` | `TEXT` | Synthesized grounded summary |
| `findings` | `JSONB` | Serialized audited `FinancialFinding` records |
| `content` | `TEXT` | Full GitHub Flavored Markdown report |
| `citations` | `JSONB` | Serialized `SourceCitation` records |
| `error_message` | `VARCHAR(500)` | Sanitized diagnostic error on failure |
| `created_at` | `TIMESTAMP` | Record creation timestamp |
| `updated_at` | `TIMESTAMP` | Record modification timestamp |

## 4. REST API Endpoints

- **`POST /api/v1/reports`** (HTTP 202 Accepted): Create and enqueue report.
- **`GET /api/v1/reports/{id}`** (HTTP 200 OK): Get report status, content, and citations.
- **`GET /api/v1/reports`** (HTTP 200 OK): List reports with optional status filtering (`?status=completed`) and pagination (`?limit=50&offset=0`).
- **`DELETE /api/v1/reports/{id}`** (HTTP 204 No Content): Delete report record (does not affect source documents or chunks).
